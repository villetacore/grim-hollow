# 10. Linux, Docker и эксплуатация

Документ описывает целевую инфраструктуру. Уже реализованные dev-Compose, Dockerfile и скрипты запуска описаны в [практической инструкции](13-running.md); production, CI-релиз и эксплуатационные гарантии ниже ещё предстоит реализовать и проверить.

## Среды и сервисы

Основная среда — поддерживаемый Linux LTS x86-64 с Docker Engine и Compose v2. Локальная разработка допускает Docker Desktop/WSL2, но серверные проверки проходят в Linux. Production начинается с Compose и понятного резервного копирования.

| Сервис | Процесс | Доступ |
| --- | --- | --- |
| edge | Nginx, HTTPS/WSS reverse proxy | Публично 443; 80 только редирект/ACME при необходимости |
| api | PHP-FPM + Laravel | Только внутренняя сеть |
| world | PHP CLI event loop | Только через edge, внутренний admin port |
| queue | Laravel queue worker | Внутренняя сеть |
| scheduler | Один Laravel scheduler | Внутренняя сеть |
| mysql | MySQL 8.4, persistent volume | Без публичного порта |
| redis-cache | Cache/presence/rate limits | Без публичного порта, TTL и eviction |
| redis-queue | Job queue | Без публичного порта, noeviction и AOF |
| metrics/logs | Сбор метрик и журналов | Доступ оператора |

В dev можно использовать один Redis при отсутствии ценных данных. `api`, `world`, `queue`, `scheduler` строятся из одной версии приложения с разными командами запуска. Контейнеры приложения работают от непривилегированного пользователя. Изменяемые данные находятся в явных volumes; исходники в production не монтируются с хоста.

## Конфигурация

Будущий `.env.example` содержит только имена и безопасные образцы: `APP_ENV`, `APP_KEY`, `PUBLIC_BASE_URL`, `DB_HOST`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `REDIS_CACHE_HOST`, `REDIS_QUEUE_HOST`, `WORLD_NODE_ID`, `WORLD_TICK_MS`, `CONTENT_VERSION`, `ASSET_BASE_URL`. Настоящие секреты передаются файлами Docker secrets или менеджером секретов и не входят в Git/образ.

Версии PHP-зависимостей фиксируются composer.lock, образы — проверенными digest, Pascal toolchain — манифестом сборки. Политика обновлений: регулярное окно, тестовый стенд, проверка протокола и миграций, затем выкладка. Использование «latest» в production не допускается.

## CI и доставка

1. Проверка PHP-стиля, статического анализа и unit tests правил.
2. Интеграционные тесты на настоящем MySQL и Redis: блокировки, индексы, повтор операций.
3. Валидация контента, ссылок локализации, карт и JSON Schema.
4. Сборка Pascal-клиента на Linux и Windows, тесты сериализации на общих fixtures.
5. Сквозной тест двух клиентов, перезапуск world-процесса и проверка наград.
6. Сборка образов, SBOM и проверка известных уязвимостей; подпись клиентской поставки.
7. Staging: миграции, smoke test, нагрузочный профиль; публикация артефактов для выпуска.

Миграции сначала расширяют схему совместимыми столбцами, затем обновляется приложение, позже удаляется старое. Опасные изменения выполняются отдельно после резервной копии и репетиции. Откат образа не означает откат данных: разрушительные миграции не входят в обычную выкладку.

World-узел переводится в drain: прекращает новые размещения, сообщает о техническом окне, завершает активные экспедиции. Принудительная остановка использует тот же механизм восстановления, что авария. Две версии контента могут жить параллельно до завершения старых забегов; протокол клиента должен поддерживать все активные серверные версии.

## Наблюдаемость и цели

| Показатель | Начальная цель / реакция |
| --- | --- |
| Такт world | p95 обработки ≤ 50 мс, p99 ≤ 80 мс при периоде 100 мс |
| Перерасход такта | > 1% за 5 минут: остановить размещение новых зон на узле |
| HTTP API | p95 ≤ 300 мс на обычных запросах, без загрузки ресурсов |
| Подтверждение действия | p95 ≤ 250 мс при сетевом RTT ≤ 100 мс |
| Восстановление world | Цель ≤ 60 с без потери подтверждённых экономических операций |
| Доступность после beta | Цель 99,5% в месяц, затем пересмотр по эксплуатационным данным |

Это критерии будущего нагрузочного теста, не результаты измерений. Для всех метрик указываются аппаратная конфигурация, число игроков, распределение зон и версия контента.

Логи структурированы: timestamp, level, request_id, instance_id, character_id, command_id, owner_epoch, event_seq. Пароли, токены, билеты и полное тело чата в обычные технические логи не пишутся. Метрики: CCU, количество зон, задержка записи журнала, размер исходящих очередей, reconnect, ошибки финализации, лаг outbox, MySQL deadlocks, памяти на инстанс.

Readiness world означает доступность БД, загрузку контента и возможность владеть зоной; liveness означает работающий event loop. При перегрузке readiness снимается, но процесс не убивается бесконечными автоматическими рестартами.

## Резервное копирование

Ежедневная полная резервная копия MySQL, binlog для восстановления на момент времени, шифрованная копия вне основного узла. Черновая retention: 7 ежедневных и 4 еженедельных; окончательная зависит от стоимости и требований к данным. Ключи шифрования хранятся отдельно от архивов.

Для полной потери узла целевые RPO ≤ 5 минут и RTO ≤ 2 часов; это отличается от восстановления отдельного процесса, где уже подтверждённые операции остаются в живой БД. Реплика не заменяет backup. Восстановление проверяется ежемесячно на отдельном стенде с пересчётом кошельков и сверкой settlement.

Порядок восстановления: остановить запись → восстановить БД и binlog → сверить версию приложения/контента → увеличить эпохи владельцев → восстановить зоны → повторить outbox → выполнить сверку → открыть вход. Если зона невосстановима, не генерировать награду заново; закрыть её административным исходом и выполнить аудируемую компенсацию по последнему подтверждённому состоянию.

## Безопасность

Сервер валидирует каждое действие и доступ к сущности. Подмена позиции, cooldown, количества расходников и результата боя невозможна через допустимый протокол. Передача скрытых врагов запрещена по правилам области видимости. Читы на автоматизацию не решаются одной авторитетностью сервера: используются лимиты, анализ повторяющегося поведения и ручная проверка спорных случаев.

Авторизация: современное хэширование паролей средствами Laravel, ограничения входа, отзыв устройств; для административной панели MFA и отдельные роли. Админские изменения требуют причины. HTTPS обязателен, CORS для веб-панели ограничен, браузерные формы защищены CSRF; нативный клиент использует bearer-сессию.

Определены сроки хранения аккаунтных данных, чата и аудита, экспорт/удаление пользовательских данных и доступ поддержки. Конкретная юридическая политика оформляется для выбранных стран запуска; этот документ не объявляет соответствие какому-либо закону.

## Эксплуатационные инструкции, которые нужно написать

- Недоступна БД: пауза симуляции, остановка финализаций, восстановление связи и идемпотентный повтор.
- Потерян Redis: восстановление присутствия/маршрутизации из источников истины, повтор outbox.
- Утёк токен или ключ: отзыв, ротация, аудит диапазона затронутых сессий.
- Обнаружено дублирование предметов: приостановка рынка, сохранение доказательств, сверка проводок и адресное исправление.
- Перегрузка: запрет новых размещений, очередь входа, добавление узла; уменьшение сложности симуляции без предупреждения игрокам не применяется.
