# 08. HTTP API и игровой протокол

Это **целевая** спецификация первого протокола. Текущий прототип использует подмножество с упрощениями: полные snapshots, UUID команды, `attack/bash` вместо общего `use_skill` и локальный HTTP-клиент. Его действующие маршруты находятся в `apps/server/routes/api.php`; различия перечислены в [статусе](00-implementation-status.md). Формат — UTF-8 JSON, координаты и длительности целочисленные. Полный общий OpenAPI/JSON Schema и двусторонняя проверка всех полей остаются этапом S0.

| POST /api/v1/auth/register | Регистрация | Public, rate limit, подтверждение email |
| POST /api/v1/auth/login | Получение сессии | Public, rate limit по IP и аккаунту |
| POST /api/v1/auth/refresh | Ротация пары токенов | Refresh token, одноразовое использование |
| POST /api/v1/auth/logout | Отзыв устройства | Сессия |

| POST /api/v1/reports | Жалоба | Аккаунт, rate limit |

Маршруты друзей, гильдий и администрирования уточняются на этапе социальных систем. Административные маршруты имеют отдельные разрешения и аудит. Владелец проверяется сервером при каждом запросе, даже если клиент не показывает чужие ID.

Пагинация: `cursor`, `limit` 1–100, ответ `items`, `next_cursor`. Старт экспедиции возвращает 202 и ID; размещение проверяется GET-запросом. Долгие операции не удерживают HTTP-соединение.

Ошибки HTTP: 400 — синтаксис, 401 — сессия, 403 — права, 404 — недоступная сущность, 409 — конфликт состояния/ревизии, 422 — ошибочные поля, 429 — ограничение частоты, 503 — временная недоступность. Тело: `error.code`, `error.message_key`, `error.fields`, `request_id`, `retryable`. Клиент локализует ключ и показывает request_id для поддержки.

`Idempotency-Key` — случайный UUID. Ключ связывается с аккаунтом, маршрутом и хэшем нормализованного тела. Повтор с другим телом даёт 409; параллельный незавершённый запрос — `operation_in_progress`. Общие HTTP receipts хранятся 7 суток; уникальность экономического основания и settlement сохраняется весь срок хранения операций.

## Авторизация и WSS

Access token действует 15 минут, refresh — 30 дней, хранится на сервере в виде хэша и ротируется. Повторное использование уже погашенного refresh отзывает цепочку устройства. Реализация выбирается отдельно: собственные opaque-сессии поверх Laravel auth, без заявления, что стандартный Sanctum автоматически реализует этот жизненный цикл.

Клиент получает билет через HTTPS. Билет живёт 30 секунд, используется один раз и привязан к персонажу, instance_id и connection_generation. После установления WSS клиент отправляет `hello` с билетом за 5 секунд; билет не идёт в URL. До успешного `welcome` остальные сообщения запрещены. TLS-сертификат и имя хоста проверяются клиентом.

```json
{
  "v": 1,
  "type": "hello",
  "ticket": "opaque-one-time-ticket",
  "client_build": "0.1.0",
  "content_version": "prototype-001",
  "last_event_seq": "0"
}
```

Сервер отвечает `welcome` с session_id, instance_id, connection_generation, tick rate, content version, expected command_seq и минимальной версией клиента, затем snapshot. Несовместимые версии отклоняются до входа в бой.

## Команды и события

Пример намерения движения после аутентификации:

```json
{
  "v": 1,
  "type": "command",
  "command_id": "01K00000000000000000000001",
  "command_seq": "42",
  "connection_generation": "3",
  "payload": {"action": "move", "direction": "north"}
}
```

Позицию, время исполнения, урон, награду и персонажа клиент не назначает. Персонаж уже связан с соединением. Разрешённые действия v1: `move`, `use_skill`, `use_consumable`, `interact`, `select_relic`, `set_ready`, `extract`, `cancel_queued_action`. У каждого отдельная схема payload.

`command_ack` подтверждает приём, а не успешное действие. После такта приходит `command_result` со статусом `executed`, `rejected` или `replaced` и причиной. Receipt связывает command_id с хэшем payload. Повтор с тем же ID возвращает прежний результат; другой payload с тем же ID — ошибка. Пропуск command_seq вызывает запрос синхронизации, а не исполнение вне порядка. Старые команды не исполняются повторно после reconnect.

```json
{
  "v": 1,
  "type": "world_delta",
  "instance_id": "01K00000000000000000000002",
  "tick": "1842",
  "event_seq": "992",
  "base_revision": "317",
  "revision": "318",
  "changes": [
    {"entity_id": "01K00000000000000000000003", "x": 12, "y": 8, "hp": 74}
  ]
}
```

`event_seq` — позиция подтверждённого глобального журнала инстанса; видимая клиенту выборка может пропускать скрытые события. Непрерывность клиент проверяет по своей `revision`, не по глобальному event_seq. Snapshot содержит revision, подтверждённый tick, видимую карту, доступные сущности, публичные эффекты и последний результат команды. Delta имеет `base_revision`; несовпадение требует нового snapshot. Удаление или исчезновение сущности из обзора передаётся явно.

Другие серверные сообщения: `combat_log`, `inventory_changed`, `expedition_state`, `chat_message`, `server_paused`, `resync_required`, `error`. Snapshot разбивается на страницы по 64 KiB с snapshot_id, номером и общим количеством; клиент применяет его только целиком. Пока snapshot не собран, ввод боя заблокирован, дельты буферизуются ограниченно.

## Задержка и защита канала

Ping каждые 10 секунд, отсутствие ответа 30 секунд закрывает соединение. Переподключение с задержками 1, 2, 4, 8 секунд с jitter, затем не чаще раза в 15 секунд до истечения 120-секундного окна. Билет запрашивается заново; потерянная команда повторяется с прежним ID только после согласования sequence.

Входящее игровое сообщение ≤ 4 KiB; обычное исходящее ≤ 64 KiB; максимум собранного snapshot 2 MiB. На snapshot не включаются невидимые противники, будущие комнаты и чужой инвентарь. Частота команд — 20/с, burst 40, чат — 1/с, burst 5. Эти начальные пределы уточняются тестами. Ограничения также применяются по аккаунту и IP, чтобы reconnect не сбрасывал защиту.

При переполнении исходящей очереди некритические промежуточные позиции заменяются последними; обязательные результаты операций сохраняются в receipts. Если очередь > 1 MiB, сервер требует resync; медленный клиент не тормозит симуляцию. Сжатие WebSocket для v1 выключено ради ограничения расхода CPU и памяти; JSON сначала проверяется по размеру, затем парсится с ограничением глубины.
