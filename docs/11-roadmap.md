# 11. План реализации и критерии готовности

## Первая игровая поставка 0.3.0

Реализованы четыре класса, три области кампании, городские службы, ремесло, рынок, гильдии, друзья, таланты, поднятие союзника, модерация и обновлённый пиксельный клиент со справочником. Проверены MySQL, Windows WebSocket, отзыв сессии, restart и replay. [Границы первой версии](15-first-version.md), [фактические результаты](00-implementation-status.md).

Следующие пункты S0–S4 ниже — план полноценной MMO. Они не являются оставшимися мелкими исправлениями этого обновления и не считаются выполненными.

## Этапы

Оценки ниже — ориентиры для команды из 4–6 человек: разработчик сервера, Pascal-разработчик, технический геймдизайнер, художник, QA и частичное участие DevOps/звука. Это не обещание сроков. Один разработчик должен существенно сократить объём; сроки нельзя получить простым делением на число участников.

| Этап | Ориентир | Результат и условие перехода |
| --- | --- | --- |
| S0. Технические риски | 2–3 недели | Pascal подключается по проверенному TLS/WSS; два клиента видят движение; 10 Гц подтверждены; выбран toolchain |
| S1. Вертикальный срез | 6–8 недель | Один класс, 3 этажа, 4 врага, босс, 2 игрока; полный цикл с сохранением и восстановлением |
| S2. Закрытая alpha | 8–12 недель | 4 класса, группы до 4, город, 2 биома, профессии, друзья, чат; 100 CCU на измеренном стенде |
| S3. Экономика и beta | 8–12 недель | 3 биома, торговая доска, гильдии, модерация, обновления клиента, restore drill; устойчивость на длительном тесте |
| S4. Подготовка релиза | 4–8 недель | Баланс, обучение, локализация, доступность, поддержка, договорённая эксплуатационная готовность |

Последовательная сумма ориентиров — 28–43 недели, с возможным увеличением после S0/S1. Внешнее тестирование, производство графики и переработка баланса могут стать критическим путём. Масштаб 1000 CCU — отдельный последующий эксперимент, не критерий первого релиза.

## S0: конкретный порядок задач

1. Зафиксировать версии PHP/Laravel, Pascal, SDL2 bindings и сетевой библиотеки.
2. Создать Laravel skeleton и Docker dev-окружение, health checks, MySQL migrations для минимальных аккаунтов/героев.
3. Создать contracts v1, валидные/невалидные fixtures и двусторонние тесты сериализации.
4. Запустить CLI event loop с одной зоной 32×32 и статическими препятствиями.
5. Собрать клиент: окно, тайлы, ввод, HTTPS-вход, WSS-ticket, snapshot/delta.
6. Подключить два клиента, затем ботов; измерить RTT, частоту такта, память и запись журнала.
7. Прервать соединение и world-процесс, восстановить состояние, сверить контрольную сумму.

Критерий завершения: есть воспроизводимая сборка и отчёт с измерениями. Если TLS/WSS или рендерер нестабилен, меняется адаптер/библиотека до написания большого объёма игры.

## Стратегия проверок

**Правила:** unit tests урона, сопротивлений, cooldown, зарядов и состояний; property tests сохранения количества предметов, отсутствия отрицательных балансов, связности карт. Тесты проверяют инвариант, а не дублируют формулу реализации строчка в строчку.

**Детерминизм:** фиксированные seed, команды, версии и начальное состояние дают одинаковый хэш результата. Тесты выполняются на целевой версии PHP. Порядок перебора коллекций и сериализации фиксирован; replay не зависит от текущего времени.

**Транзакции:** параллельная покупка одного лота, два получения вложения, повтор crafting, double settlement, deadlock/retry, одинаковый idempotency key с другим payload. Проверка на MySQL, а не замена SQLite, потому что различаются блокировки и ограничения.

**Сеть:** задержка 50/100/250 мс, разрыв соединения, повтор прикладной команды после reconnect, потеря ответа HTTP, медленный потребитель, неправильная revision, повреждённый JSON и слишком большой пакет. WSS уже сохраняет порядок в рамках одного соединения; тестируется порядок команд приложения между соединениями, а не выдуманная перестановка TCP-кадров.

**Аварии:** kill владельца до/после commit, старый владелец после истечения аренды, Redis restart, временная недоступность MySQL, сбой при settlement, восстановление backup. Игрок не получает и не теряет подтверждённые активы из-за повторного выполнения.

**Нагрузка:** ступени 10 → 50 → 100 CCU; профиль 20% город, 80% экспедиции, по 4 игрока и до 40 активных врагов на экспедицию. Часовой soak test после достижения цели; фиксируются CPU, RAM, IOPS, сеть, размер журнала и p95/p99. Боты выполняют реальные команды и проходят тот же протокол.

## Основные риски

| Риск | Ранний сигнал | Ответ |
| --- | --- | --- |
| PHP не укладывается в такт | p99 > 100 мс, очередь записи растёт | Профилировать, уменьшить число зон на процесс, оптимизировать правила; выделять горячий компонент только по измерениям |
| Сложности Pascal WSS/TLS | Сбои reconnect/сертификатов на чистой ОС | Технический spike S0, смена адаптера до производства контента |
| Конфликт MMO и пошаговости | Игрок ждёт чужих действий | Фиксированные такты, отсутствие общей паузы, ограниченная очередь намерений |
| Дублирование активов | Несогласованные settlement/ledger | Уникальные основания, транзакции, outbox, аварийные тесты |
| Слишком дорогой контент | Один биом требует больше этапа | Меньше биомов, больше системных сочетаний и шаблонов |
| Поражение отталкивает | Выход после первой смерти | Понятная цена риска, облегчённые контракты, пересмотр износа |
| Экономика разгоняется | Выпуск валюты сильно выше вывода | Анализ источников, баланс ремонта и комиссий, запрет бесконтрольных выдач |
| Разрастание требований | Нет законченного цикла при множестве экранов | Заморозить S1, вести отдельный backlog после beta |

## Определение готовности функции

Функция описана данными/контрактом, реализована на сервере и в клиенте, имеет необходимые проверки инвариантов, понятные ошибки и метрики. Миграция совместима с развёртыванием, тексты локализованы, UI проверен на 1280×720, правила доступны игроку. Для операций с ценностями проверены повтор запроса и сбой между шагами.

После каждого этапа обновляются этот план, открытые решения и бюджет контента. Выбор графической библиотеки, точные формулы и лимиты нагрузки не объявляются окончательными до проверки.

## Платформы клиента (после 0.5)

**Android — нативный клиент на Free Pascal.** Без Java-кода и WebView: библиотека `libgrimhollow.so`, собранная FPC для `aarch64-android`/`arm-android`, подключается к системному `android.app.NativeActivity` (класс платформы, писать Java не нужно).
- Рендер: программная отрисовка в буфер `ANativeWindow` тем же набором примитивов, что и `GameArt`/`GameRenderer`, плюс встроенный пиксельный шрифт с кириллицей.
- Ввод: сенсорные D-pad и панель умений через `AInputQueue`; экранная клавиатура вызывается через JNI из Pascal.
- Сеть: HTTPS/WSS через системный стек Android, вызываемый через JNI из Pascal (у платформы нет публичного OpenSSL).
- Сборка: FPC-кросскомпилятор под Android, Android NDK (линковка с `libandroid`/`liblog`), `aapt2`/`zipalign`/`apksigner` из SDK. APK собирается скриптом без Gradle и в CI.

**Windows XP/Vista/7.** С 0.5 клиент загружает WebSocket-функции WinHTTP динамически: на системах до Windows 8 он запускается и играет через HTTPS-опрос. Экспериментальная 32-битная сборка на Lazarus 2.2.6 создаётся в CI.

**DOS не планируется.** Под DOS нет LCL, системного TLS и сетевого стека, а игра целиком сетевая и требует HTTPS/WebSocket к авторитетному серверу. Порт потребовал бы отдельного TCP/IP-стека (packet driver), собственной реализации TLS и текстового интерфейса. Это другой продукт, а не сборка этого клиента.
